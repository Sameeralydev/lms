## Remaining configurable-workflow implementation

- Phase 16 now stores per-user in-app alert preferences for announcement and direct-message events. Immediate and scheduled announcement dispatch and direct-message dispatch honor the recipient setting. External providers, delivery receipts, and unapproved channel-consent behavior remain a separate provider/product dependency.
- Phase 19 now has daily staff clock-in/out and tenant-configurable leave types and review workflows. The implementation uses institution-local work dates, stores clock instants in UTC, counts leave calendar days and supports an optional per-request maximum; it does not calculate leave balances, working days, statutory entitlements, shifts, payroll, or compensation. Recruitment, onboarding, sensitive document retention, performance review, and HR reporting still require their approved business workflows and policies.
- New additive migrations are `2026_11_18_000000_create_communications_notification_preferences.php` and `2026_11_18_000001_create_hr_attendance_and_leave.php`. Neither was executed; the configured database has not been verified as an authorized Developer B schema.
## Scope decision summary

- No standalone acceptance matrices for Phases 16 or 19–23 were present. The matrix uses the assignment briefs, phase discovery reports, module boundaries, and the Phase 03 standards mapping; it does not infer conditional examples as committed requirements.
- CASE is the only education standard concretely named by the standards map. The current API is a useful, tenant-bound read-provider subset and is not full CASE conformance. An import consumer is not treated as approved merely because the generic Phase 22 template lists import/export as a possible integration capability: no consumer direction, fields, persistence rules, or import policy are specified. The decision remains a functional scope dependency, not QA.
- No database migrations were executed. The configured database has not been positively verified as an isolated, authorized Developer B schema.
- Verification marked QA PENDING in this matrix refers only to unrun checks. It does not disguise missing implementation or unresolved product decisions.
